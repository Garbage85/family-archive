# Контекст проекта Family Archive

## 1. Назначение проекта

Family Archive — современный self-hosted семейный архив с генеалогическим деревом.

Проект предназначен не только для хранения структуры родства. Его основная задача — сохранять семейную историю на десятилетия:

- людей;
- биографии;
- фотографии;
- видео;
- документы;
- воспоминания;
- события;
- места;
- родственные связи.

Генеалогическое дерево является основным способом навигации, но не единственным содержанием продукта.

## 2. Продуктовая философия

Family Archive создаётся как частное семейное пространство, а не как социальная сеть или публичный генеалогический сервис.

Основные принципы:

- данные принадлежат семье;
- приватность важнее публичности;
- архив должен работать локально и независимо от внешнего сервиса;
- данные должны переживать обновления, смену оборудования и смену администраторов;
- интерфейс должен быть понятен обычным членам семьи;
- автоматизация не должна создавать неподтверждённые родственные связи;
- важные действия должны быть обратимыми или подтверждаемыми.

## 3. Целевая платформа

Основная целевая платформа:

- Raspberry Pi 5;
- Linux ARM64;
- Raspberry Pi OS / Debian;
- домашний self-hosted сервер.

Проект должен устанавливаться и обслуживаться человеком без глубоких знаний системного администрирования.

## 4. Технологический стек

### Frontend

- Vite.
- Family Chart для визуализации дерева.
- Собственные компоненты и формы Family Archive.
- Встроенный редактор Family Chart рассматривается как временный и должен быть заменён.

### Backend

- PocketBase.
- Хранение данных и медиа.
- Миграции схемы.
- В перспективе нормализованная модель людей, семей, связей и участников.

### Развёртывание

- systemd.
- CLI `family-archive`.
- Production frontend размещается в `pb_public`.
- Используется Git и отдельные экспериментальные ветки.
- Текущий systemd unit исторически может называться `family-tree.service`.

## 6. Основные функциональные направления

### 6.1. Семейное дерево

Дерево должно:

- показывать людей и их связи;
- отображать родителей, детей, супругов, братьев и сестёр;
- поддерживать переход к карточке человека;
- работать на desktop и мобильных устройствах;
- корректно отображать линии связей;
- в будущем поддерживать полное дерево без потери родственников и супругов боковых ветвей.

Family Chart используется как движок отображения. Продуктовая логика и редактирование принадлежат Family Archive.

### 6.2. Карточка человека

Карточка человека является центральной сущностью архива.

В перспективе она содержит:

- ФИО;
- пол;
- даты жизни;
- места;
- биографию;
- фотографии;
- документы;
- события;
- родственников;
- воспоминания;
- связь с пользовательским аккаунтом.

Списки родственников должны быть интерактивными и открывать соответствующие карточки.

### 6.3. Создание родственников

Форма добавления родственника должна учитывать контекст.

Планируется умное автозаполнение:

- предложение фамилии;
- предложение отчества;
- возможное определение пола по отчеству;
- перенос очевидных данных из контекста;
- предложение существующей связи.

При добавлении второго родителя система может предложить связать нового родителя с уже существующим как супругов. Предложение может быть отмечено по умолчанию, но пользователь должен иметь возможность отказаться.

Автоматическое изменение родственных связей без подтверждения запрещено.

### 6.4. Пользователи и роли

Базовые технические роли:

- owner;
- admin;
- editor;
- member;
- guest.

Обсуждались семейные названия:

- Владелец → «Глава семьи»;
- Администратор → «Хранитель очага»;
- Редактор → «Член семьи»;
- Участник → «Друг семьи»;
- Гость → «Гость».

Окончательная схема прав должна сохранять однозначность и не зависеть только от красивых названий.

Ключевое принятое правило: пользователь с ролью «Член семьи» обязательно связан с конкретной карточкой человека в дереве.

### 6.5. Приглашения

В карточке живого человека предусматривается действие «Пригласить родственника».

Система создаёт персональную ссылку:

- ссылка относится к одной карточке;
- по ней пользователь регистрируется или входит;
- пользователь автоматически добавляется в архив;
- ему назначается роль «Член семьи»;
- аккаунт связывается с указанной карточкой;
- после использования ссылка становится недействительной;
- администратор может отозвать ссылку;
- у одной карточки не должно быть нескольких активных приглашений одновременно.

### 6.6. Гостевой доступ

Неавторизованный пользователь может видеть только дерево.

Он не должен получать доступ:

- к карточкам людей;
- к биографиям;
- к документам;
- к фотографиям и другим личным данным.

### 6.7. Настройки и интерфейс

Desktop-боковая панель признана неудобной.

Для полноценных форм и настроек предпочтительно центральное окно или диалог.

Также зафиксированы требования:

- убрать непонятную кнопку «человек с плюсом»;
- убрать дублирующее поле пола;
- не использовать placeholders вместо постоянных подписей;
- исправить перенос длинных имён на мобильных устройствах;
- сохранять единообразие собственных форм.

## 7. Архитектурное направление

Текущая модель PocketBase изначально включает коллекции `trees`, `proposals` и `media`.

Рассматривается переход к нормализованной структуре:

- `families`;
- `people`;
- `parent_child_links`;
- `relationships`;
- `memberships`;
- отдельные сущности для приглашений и прав.

Переход должен выполняться отдельной миграцией с отчётом:

- количество людей;
- количество связей;
- потерянные ссылки;
- циклы;
- дубликаты;
- ошибки преобразования.

Для передачи данных в Family Chart предполагается отдельный адаптер, например `buildFamilyChartProjection()`.

## 8. Установщик и эксплуатация

Установщик должен покрывать полный жизненный цикл:

- install;
- update;
- backup;
- restore;
- rollback;
- doctor;
- uninstall;
- миграции;
- systemd;
- PocketBase.

Требования:

- повторный запуск не должен разрушать рабочую установку;
- обновление не должно терять данные;
- резервная копия должна проверяться;
- rollback должен быть понятным и документированным;
- CLI должен показывать фактическое имя systemd unit;
- диагностика должна выявлять несовместимую ОС, архитектуру, зависимости, права и состояние PocketBase;
- миграции не должны требовать ручного редактирования production-базы.

## 9. Известные технические долги

- Несогласованность имени CLI `family-archive` и unit `family-tree.service`.
- Нет полноценного набора автоматических тестов.
- Нет обязательного CI.
- Не все рисковые сценарии дерева покрыты проверками.
- Backup/restore нуждаются в проверке целостности и тестовом восстановлении.
- Требуется усиление политики безопасности, rate limiting и приватности.
- CSP допускает inline styles из-за ограничений библиотеки.
- Старые deploy/update-скрипты могут предполагать конкретные пути и копировать только frontend.
- Директория миграций не должна оставаться без необходимости доступной на запись сервису.

## 10. Принцип развития

Все явно утверждённые продуктовые решения считаются частью технического задания.

Эксперименты допустимы, но не должны ухудшать стабильную версию.

Проект должен развиваться постепенно:

1. Зафиксировать стабильную модель данных.
2. Закрыть критические сценарии дерева проверками.
3. Заменить встроенный редактор собственными формами.
4. Развить пользователей, роли и приглашения.
5. Усилить установщик, обновление, backup и rollback.
6. Добавлять архивные функции: медиа, документы, события, воспоминания и поиск.
